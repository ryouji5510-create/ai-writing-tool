# Streamlit + Gemini セキュリティ監査

フォルダ全体を対象に、Streamlit + Gemini API アプリ特有のリスクを調べ、レポートだけを出す。コードは変更しない(修正は、ユーザーがレポートを見て依頼したときに別作業として行う)。差分ではなく現状のコード全体を見るので、Git管理されていなくてもよい。

## 手順

1. **対象を把握する。** Glob で `*.py`, `requirements*.txt`, `.streamlit/*`, `.gitignore`, `.env*`, `Dockerfile` などを列挙する。主要な `.py` は全文読む。短い個人ツールが多いので、grepだけで済ませず実際に読むほうが、文脈に依存する問題を見逃さない。
2. **機械的スキャンを走らせる。** `python <このスキルのパス>/scripts/scan.py <対象フォルダ>` を実行すると、危険パターンの出現箇所が `ファイル:行` で出る。これは候補の洗い出しにすぎない。ヒットごとに前後を読み、実際に問題かを判断する(誤検知は報告しない)。
3. **下の観点で手動確認する。**
4. **レポートを書く**(形式は後述)。

## 観点

### A. APIキー・秘密情報(最優先)
- コードや設定にキーが直書きされていないか(`AIza` で始まる文字列、`api_key="..."`)。
- `.env` などが `.gitignore` に入っているか。`.env` に実キーが残っていないか(ファイルの存在と、ignore されているかだけを確認し、キーの値そのものはレポートに書かない。一部でも転記すると、レポート自体が漏えい源になる)。
- キーの保持先。`st.session_state` はセッション単位で安全。モジュールのグローバル変数、`st.cache_resource`、`os.environ` への代入は、別ユーザーのセッションと共有されうるので危険。
- キーが `print` / `logging` / `st.write` / エラー表示 / URLクエリ(`st.query_params`)に出ていないか。
- `st.cache_data` / `st.cache_resource` の引数にキーを渡している場合、キャッシュはサーバーのメモリ上で全セッション共通になる。引数は内部でハッシュされるが、返り値が別ユーザーに渡らないかを確認する。

### B. 入力と出力の扱い
- `unsafe_allow_html=True`、`st.components.v1.html`、`st.html` にユーザー入力やモデル出力を渡していないか(XSS)。モデルの出力は信頼できない入力として扱う。
- `eval` / `exec` / `subprocess` / `os.system` / `pickle.load` / `yaml.load` にユーザー入力やモデル出力が届かないか。
- ユーザー入力をプロンプトに埋め込む箇所(プロンプトインジェクション)。ツール呼び出しやファイル・ネットワークアクセスをモデルに与えていないなら影響は「出力の質」止まりで低リスク。与えているなら高リスクとして扱う。
- ファイルアップロードがあれば、サイズ・拡張子の制限、保存先パス(パストラバーサル)。

### C. 情報漏えい・プライバシー
- 例外をそのまま `st.error(str(e))` で出している場合、内部パスやリクエスト内容が出ないか。個人利用なら低、公開するなら中。
- 入力文章はGoogleに送信される。無料枠では入力が品質改善に使われる場合がある点を、機密文書を扱う用途ならレポートの注意事項として書く。
- 履歴などを `st.session_state` 以外(ファイル・グローバル・`st.cache_*`)に保存していないか。共有状態に入れると、別ユーザーに見える。

### D. 公開時の設定(公開・デプロイを検討している場合に重点)
- `.streamlit/config.toml` の `server.enableXsrfProtection` / `enableCORS` を無効化していないか。
- `server.address=0.0.0.0` で認証なしに公開していないか。HTTPS(リバースプロキシや Streamlit Community Cloud)を通しているか。利用者のAPIキーが通信路を流れるため、HTTPSは必須。
- 認証なし・サーバー側キーなしの設計なら、乱用による課金リスクは利用者自身のキーに閉じる。サーバー側にキーを置く設計に変えると、入力長・回数の制限が必要になる。

### E. 依存関係
- `requirements.txt` のバージョン固定の有無。`pip-audit` が入っていれば `pip-audit -r requirements.txt` を実行する。未導入なら入れずに、実行を提案するにとどめる。
- 見知らぬパッケージ、タイポスクワッティングの疑い。

## レポート形式

必ず日本語で、この構成にする。

```
# セキュリティ監査レポート: <アプリ名>
対象: <フォルダ> / 確認したファイル: <一覧> / 日付

## 総評
(2〜3行。公開しても大丈夫か、を結論から)

## 指摘事項
| # | 重大度 | 場所 | 内容 |
(重大度: 高 / 中 / 低 / 情報。高=直ちに直す、中=公開前に直す、低=余裕があれば、情報=知っておくべき注意)

### 1. <指摘のタイトル>
- 場所: `ファイル:行`
- 問題: ...
- 影響: 誰が何をできてしまうか(具体的に)
- 修正案: 具体的なコード方針

## 問題なしと確認した項目
(確認して安全だった観点。何を見たかが分かるように)

## 未確認・前提
(見ていない範囲、公開形態の仮定)
```

- 指摘は、実際に悪用経路を説明できるものだけにする。「一般論としてあり得る」だけのものは「情報」に回すか書かない。件数を稼ぐより、読んだ人が動ける精度が大事。
- 問題が見つからなければ、そう書く。無理に指摘を作らない。
- 「問題なしと確認した項目」を省かない。何を見て安全と判断したかが分かると、レポートの信頼性が上がる。
